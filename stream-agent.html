Case study 2 · Redesign · Agentic workflow

An agent that adds and maintains stream subgraphs

Adding a new immigration stream to the eligibility knowledge graph meant reading the official page, breaking it into requirements and conditions, linking them to the shared ontology, and validating the result. Keeping streams current meant repeating part of that whenever a page changed. This page shows how I would build that as an agent today.

A redesign, not the shipped system. The graph model, the condition language, and the maintenance playbook on this page are what I built. The agent below is my design for automating that playbook with LangGraph and a vector store, written as a system-design exercise.

What retrieval is for

Three collections, each answering one question:

  1. Source chunks: section-aware chunks of official pages, with stream, URL, heading path, anchor, and extraction date. Where did this rule come from, and what changed near it?
  2. Ontology catalog: shared concepts and existing conditions, with their descriptions. Is this already defined?
  3. Profile schema: every profile pointer with a description and example values. Which field holds this fact?

The main job of retrieval here is reuse: before the agent creates a condition, it searches for an existing concept that means the same thing. A new stream that asks for "one year of skilled work" should reference the shared definition, not add a sixth copy of 1,560 hours.

Retrieval proposes candidates, the model chooses or says "none fits", and code verifies the choice: the concept ID exists, the pointer exists in the profile schema. A new concept or a new profile field is never created silently; it goes to review, flagged.

How I would know it works

The hand-built streams are the test set. Replay their stored source snapshots through the agent and compare its subgraph with the one people wrote.

MeasureWhat it catches
Same outcomes on seed profilesThe one that matters: qualified, possible, and disqualified match the hand-built subgraph on every seed profile, even if the graph is shaped differently
Requirement coverageBlocks of eligibility the agent missed or invented
Reuse rateConditions linked to existing shared concepts, against near-duplicates it created

Reviewer editsHow much a person had to change before approving, tracked over time

What stays deterministic

  1. Only the commit step writes to the graph, in one transaction, after a person approves.
  2. IDs stay stable when meaning is unchanged, so evaluation history and analytics keep pointing at the same conditions.
  3. Changes are versioned with valid_from / valid_to rather than overwritten, so an application can be evaluated against the rules in force on the day it was submitted.
  4. Every condition keeps its source anchor and quoted span. That is what makes change localization a lookup instead of a search.
  5. Anything the agent cannot resolve, such as an unmatched pointer or a new concept, stops the run loudly and goes to review. Nothing is guessed.
